# Demo checkpoint 3 — backup capture checklist

Version 1.0. Supersedes nothing; first version.

Raised by the phase-3 flag review. The phase-3 prompt asked for a backup screen
capture at demo checkpoint 3 (the idea-stage submission build, 4 September). Part
of that is done and part of it is a human task; this file exists so the human part
is recorded somewhere that outlives a phase report.

## What already exists

Sixteen committed visual-regression baselines — four screens × two themes × two
platforms — under `apps/web/e2e/visual.spec.ts-snapshots/`. These are captures of
the real built dashboard against the real API and the 18-station demo corpus, taken
by Playwright, not mock-ups:

| Screen | Files |
|---|---|
| Network map | `map-{dark,light}-chromium-{darwin,linux}.png` |
| Station detail | `station-detail-{dark,light}-chromium-{darwin,linux}.png` |
| Data quality monitor | `quality-monitor-{dark,light}-chromium-{darwin,linux}.png` |
| Event timeline | `timeline-{dark,light}-chromium-{darwin,linux}.png` |

They are regenerated by `pnpm e2e:update` (this machine) and `make web-visual-linux`
(the pinned container). They are a *visual record*, and they are enough to prove
what the build looked like on a given commit.

## What is still outstanding — human task

A recorded screen capture of the demo being **driven**: the click path, in order,
with the narration timing. Stills cannot substitute, because the argument is a
sequence — the healthy-looking completeness figure, then the defect count beside it,
then the drill-down to one wrong-but-plausible reading and its evidence.

Suggested capture, matching the phase-3 demo path the e2e already exercises
(`apps/web/e2e/demo-path.spec.ts`):

1. `make demo` — stack, corpus, audit, API, dashboard, one command.
2. **Audit report**: conventional completeness beside the defect rate, with the
   defect-rate definition on screen next to the number.
3. **Network map**: 18 stations coloured *and* shaped by trust; note the two red.
4. Click a red station → **station detail**: the score, its component breakdown, and
   the reason codes as sentences.
5. **View evidence** → the reason-code sentence, the detector's own numbers, the raw
   series with the flagged point marked, the neighbouring stations.
6. **Event timeline**: every verdict reads "pending adjudication" — say out loud
   that the system refuses to adjudicate until phase 4 can.

Record it offline. Conference wifi fails; assume it.

## Why this is not automated

Playwright can record video (`use: { video: "on" }`), and that was considered. It
was not adopted because an automated capture races the UI rather than pausing where
a presenter would, produces no narration, and would add a large binary to every CI
run. The stills are the regression gate; the driven capture is a presentation
artefact and belongs to whoever presents.
